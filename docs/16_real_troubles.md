# 章16: 実機特有のトラブルと復帰

← [前章: 実機で搬送・アクション・可視化](15_real_delivery_action_viz.md) | [目次](../README.md) | 次章: [卒業課題とまとめ →](17_real_graduation.md)

対応する第1部: なし(実機だけの内容)。sim のトラブルは [TROUBLESHOOTING.md](TROUBLESHOOTING.md)。

## 狙い

- sim には無かった**3つの実機トラブル**を、わざと起こして復帰させる
  - BLE の切断と再接続
  - マット境界での位置ロスト
  - 起動順序を間違えたときの復旧
- 「どの端末を再起動すれば戻るか」を判断できるようになる

実機フリート運用で必ず向き合う現実がこれ。**壊れ方を知っていると、
怖がらずに運用できる**。

## 再起動の範囲 ── まずこれを頭に入れる

| 直したいもの | 再起動する端末 | 触らなくてよい端末 |
|---|---|---|
| RMF側の設定(`finishing_request`、閾値、アクションのYAML) | 端末2 | 端末1(BLE接続は維持) |
| キューブとの接続(BLE切断) | 端末1 | 端末2 ── ただし下記の注意 |
| 起動順序を間違えた(Nav2が死んだ) | **両方**(端末1 → 端末2 の順で) | ── |

## 1. BLE の切断と再接続

**起こし方**: patrol 中にキューブの電源ボタンを長押しして切る(または
Bluetoothの範囲外へ持ち出す)。

**見えるもの**:

- 端末1のブリッジが切断を報告し、`/toio1/toio/pose` の更新が止まる
- RMFの `/fleet_states` の位置が**最後の値で固まる**。RViz のマゼンタも動かない
- Nav2 はゴールに向かって指令を出し続けるが、キューブは動かない。しばらくすると
  Nav2 側でタイムアウトし、タスクが失敗または停止する

**復帰**: キューブの電源を入れ直す。ブリッジが自動で再接続するか、
再接続しない場合は端末1を再起動する。位置報告が戻ったら、止まっていたタスクを
`cancel_task` で片付け、投げ直す。

> 端末1を再起動するとき、端末2は**起動したままでよい**。Nav2 の TF 待ち
> (`initial_transform_timeout`)が効くのは**活性化時だけ**なので、すでに
> 活性化済みの Nav2 は TF が一時的に途切れても死なない。位置報告が戻れば
> そのまま続けられる。戻らなければ次節の「逆順起動」と同じ手順で全体を
> 起動し直す。

## 2. マット境界での位置ロスト

**起こし方**: go_to_place の走行中に、キューブを手でマットの端の外側へ
ずらす(またはマットの印刷が無い余白に置く)。

**見えるもの**:

- toio のPosition ID が読めなくなり、`/toio1/toio/pose` が止まる
  ([章12](12_real_go_to_place.md)の観察1で見た現象)
- BLE は繋がったままなので、ブリッジはエラーを出さない。**「繋がっているのに
  位置が来ない」**という、BLE切断より気づきにくい状態
- Nav2 は最後の位置を信じて指令を出し、キューブがマット外で空回りすることがある

**復帰**: キューブをマットの上(できれば最後に居た付近)に戻す。pose が再開し、
Nav2 が現在位置を取り直して走行を続ける。ずれが大きいときは `cancel_task` して
チャージャーへ戻し、投げ直す方が安全。

**予防**: navグラフの頂点と経路はマット内側に収めてある(A4の `approach_*` が
端から離れているのはこのため)。自分で地図を作るときも、**読み取り不能領域に
頂点を置かない**のが鉄則。

## 3. 起動順序を間違えた(逆順起動)

**起こし方**: わざと端末2(RMF+Nav2)を先に起動し、あとから端末1(ブリッジ)を
起動する。

**見えるもの**:

- 端末2で Nav2 の costmap が `map → toio1/base_link` のTFを待ち続ける
- `initial_transform_timeout`(300秒)を超えると活性化が失敗し、lifecycle manager が
  bringup 全体を中止する。**自動リトライは無い**
- あとから端末1を起動しても、Nav2 は戻らない

**復帰**: 端末2を落とし、端末1が位置を出していることを確かめてから、端末2を
起動し直す(正しい順序。[章11](11_real_robot.md))。端末1は落とさなくてよい。

> 300秒の猶予があるので、端末2を先に起動してしまっても**5分以内に端末1が
> 位置を出し始めれば間に合う**。「逆順=即死」ではなく「逆順で5分放置=死」。

## 4. 起動直後の最初のタスクが消える(再掲)

[章11](11_real_robot.md)で扱った。`Managed nodes are active` から25秒待ち、
投げたらアダプタのログで `Direct request … queued` / `Add Task` を確かめる。
出ていなければ投げ直す。これはトラブルというより**毎回の作法**。

## 理解する

- **実機の故障は「位置が来ない」に集約される**。BLE切断もマット境界も、RMF
  から見れば「ロボット層③が位置を報告しなくなった」という同じ症状。
  [章2](02_architecture.md)の「位置は別経路で上がる」という構造が、故障の
  見え方も決めている。
- **どの層が壊れたかで、再起動の範囲が決まる**。③(端末1)が壊れても①②
  (端末2)は生きている。逆に①②の設定変更で③を触る必要はない。三層モデルは
  学習用の図ではなく、運用のチェックリストになる。
- **sim は「位置が常に来る世界」だった**。だから第1部では位置ロストを扱えなかった。
  実機編でしか学べないのはここ。

## 確認課題

1. patrol 中に BLE を切り、`/fleet_states` の位置が固まるまでの時間と、Nav2 が
   諦めるまでの時間を測る。復帰後に投げ直したタスクが通ることを確認する。
2. マット外にずらしたとき、ブリッジのログに**何も出ない**ことを確認する。
   「繋がっているのに位置が来ない」を検知するには何を監視すればよいか考える
   (ヒント: `/toio1/toio/pose` の更新間隔)。
3. わざと逆順で起動し、端末1を**5分以内**に起動して Nav2 が活性化することと、
   5分放置して失敗することの両方を試す。

壊し方と直し方まで分かれば、実機フリート運用の入口に立ったことになる。
